# AI 작업 규칙

이 규칙은 이 프로젝트를 이어받는 AI와 작업자 모두가 사용한다.

## 0. 단일 작업실

- VOCA 작업은 고정된 `VOCA NEXUS 통합 작업실` 한 곳에서 계속한다.
- 새 대화, 보조 작업, 비중복 분석 작업을 자동으로 만들지 않는다.
- 조사, 구현, 검증, 배포와 브리핑을 같은 대화에서 끝까지 이어간다.
- 컨텍스트가 축약되면 새 작업을 만들지 말고 `docs/WORKING_CONTEXT.md`를 읽어 복구한다.
- 별도 작업이 반드시 필요할 때만 사용자에게 이유와 범위를 먼저 알리고 승인을 받는다.

## 1. 시작할 때

- `docs/WORKING_CONTEXT.md`를 먼저 읽는다.
- `git status`, 현재 브랜치, 최근 커밋, 원격 상태만 빠르게 확인한다.
- 이미 끝난 조사나 낡은 대화 내용을 처음부터 반복하지 않는다.
- 기존 미커밋 파일을 지우거나 reset하지 않는다.

## 2. 코드를 바꾼 뒤

- 타입 검사와 관련 테스트만으로 끝내지 않는다.
- 실제 학습 흐름을 처음부터 끝까지 확인한다.
- 기본 흐름은 `문풀 → 범위와 문제 수 선택 → 문제 풀이 → 이전·다음 → 결과 → 오답 복습 → 새로고침`이다.
- 오류와 빈 데이터에서도 안내 화면과 돌아갈 길이 있는지 확인한다.

## 3. 배포하기 전

- GitHub 로그인이 가능한지 먼저 확인한다.
- 공개 주소와 Pages 브랜치가 맞는지 확인한다.
- 프로젝트 경로 `/vocaknio-quiz/`가 HTML, JavaScript, CSS, 이미지와 글꼴에 모두 적용됐는지 확인한다.
- 이 확인이 끝나기 전에 배포 커밋이나 push를 진행하지 않는다.

## 4. 배포한 뒤

- 원격 `gh-pages` SHA가 바뀌었는지 확인한다.
- 실제 공개 사이트를 열어 새 번들이 제공되는지 확인한다.
- 홈 화면만 보지 말고 퀴즈 시작과 주요 자산 로딩까지 확인한다.
- 공개 사이트 확인 전에는 배포 완료라고 보고하지 않는다.

## 5. 브리핑 형식

작업 보고는 아래 다섯 줄을 기본으로 한다.

- 시간: 작업한 날짜와 대략적인 소요 시간
- 바뀐 점: 사용자에게 보이는 변화와 주요 파일
- 배포 여부: 미배포, 배포 준비, 배포 완료 중 하나
- 막힌 점: 인증, 테스트 실패, 사용자 결정처럼 실제 막힌 이유
- 다음 일: 바로 이어서 할 한 가지

검증은 `전용 검사 / 전체 검사 / 웹 빌드 / 공개 사이트`로 나눠 적는다.

## 6. 문서와 인수인계

- 문서에는 현재 상태, 결정 이유, 확인 결과, 다음 일만 남긴다.
- 끝난 작업 기록을 계속 덧붙여 문서를 길게 만들지 않는다.
- 낡은 설명은 최신 상태와 충돌하지 않게 고치거나 지운다.
- 개인 비밀, 인증값, 대화 원문은 저장하지 않는다.
- 사용자 결정이 필요한 일과 AI가 안전하게 계속할 수 있는 일을 구분한다.

## 짧은 인수인계 틀

```text
목표:
현재 완료:
확인 결과:
배포 상태:
막힌 점:
다음 한 가지:
수정하면 안 되는 기존 작업:
```

## 7. 최우선 명령: 요구사항 누락 방지 및 완전성 검증

이 프로젝트는 Safari와 Chrome에서 사용하는 웹 기반 영단어장 앱이다.

앞으로 작업할 때 다음 규칙을 반드시 지킨다.

1. 작업 시작 전 요구사항을 빠짐없이 체크리스트로 변환한다.
2. 사용자가 말하지 않은 요구사항을 임의로 삭제·축소·대체하지 않는다.
3. 구현이 어렵다는 이유로 기능을 생략하거나 더 단순한 기능으로 바꾸지 않는다.
4. 기존 기능과 데이터를 보존한다. 수정 범위 밖의 코드·디자인·데이터 구조를 임의로 제거하거나 초기화하지 않는다.
5. 파일을 수정하기 전에 관련 파일과 기존 구조를 먼저 확인한다.
6. 동일한 기능이 이미 구현돼 있는지 검색한 후 수정한다.
7. 모바일 Safari와 Chrome 양쪽에서 동작하는지 고려한다.
8. 브라우저별 호환성이 불확실한 API를 사용할 경우 반드시 대체 동작 또는 폴백을 구현한다.
9. 화면만 만들어 놓고 실제 로직, 저장, 불러오기, 예외처리를 누락하지 않는다.
10. 버튼·입력창·메뉴 등 모든 UI 요소가 실제 기능과 연결됐는지 확인한다.
11. 로컬 저장, 새로고침, 브라우저 재실행 후에도 데이터가 유지되어야 하는 기능은 실제로 영속성을 검증한다.
12. 요청사항과 직접 관계없는 대규모 리팩터링이나 패키지 변경은 하지 않는다.
13. 기존에 발생한 오류를 숨기기 위해 테스트를 삭제하거나 조건을 완화하지 않는다.
14. 확실하지 않은 사항은 임의로 결정하지 말고 질문한다. 단, 작업을 진행할 수 있는 부분은 먼저 진행한다.
15. 완료했다고 보고하기 전에 요구사항별 구현 여부를 직접 대조한다.

작업 절차:

A. 현재 프로젝트 구조와 관련 파일을 확인한다.
B. 사용자의 요청을 번호가 있는 체크리스트로 작성한다.
C. 각 요구사항이 어느 파일과 코드에 반영될지 정리한다.
D. 체크리스트를 기준으로 구현한다.
E. 구현 후 빌드·테스트·정적 검사·브라우저 호환성을 확인한다.
F. 각 요구사항을 다음 중 하나로 표시한다.
   - 완료
   - 부분 완료
   - 미완료
   - 확인 필요
G. 부분 완료나 미완료 항목이 하나라도 있으면 전체 작업을 완료했다고 표현하지 않는다.
H. 테스트하지 못한 사항을 “정상 작동한다”고 단정하지 않는다.

특히 자주 누락되는 다음 항목을 반드시 점검한다.

- 단어 추가·수정·삭제
- 중복 단어 처리
- 검색·필터·정렬
- 뜻, 동의어, 반의어, 예문 등 모든 필드의 저장과 표시
- 학습 상태와 암기 여부 저장
- 새로고침 후 데이터 유지
- 모바일 화면 반응형 배치
- Safari의 입력창, 터치, 스크롤, 저장 기능
- Chrome의 입력창, 클릭, 스크롤, 저장 기능
- 빈 값, 긴 텍스트, 특수문자 입력
- 오류 메시지와 예외처리
- 기존 데이터와의 호환성
- 뒤로가기 및 화면 전환
- 다크모드가 있다면 모든 화면에 일관되게 적용
- 접근성: label, 키보드 조작, 포커스 표시

최종 보고 형식:

1. 구현한 내용
2. 수정한 파일
3. 요구사항별 검증표
4. 실행한 테스트와 결과
5. 직접 검증하지 못한 항목
6. 남아 있는 문제
7. 다음에 해야 할 작업

코드가 작성됐다는 사실과 기능이 완성됐다는 사실을 구분한다. 기능 구현, UI 연결, 데이터 저장, 예외처리, 테스트까지 확인된 경우에만 “완료”라고 판단한다.

이 명령은 이후의 개별 작업 지시보다 우선하는 상시 규칙이다.

## 8. 최우선 규칙: 실제 배포 완료 검증

이 작업에서 “코드 구현 완료”, “빌드 성공”, “로컬 실행 성공”은 “배포 완료”를 의미하지 않는다.

다음 조건을 모두 충족해야만 작업을 “완료”라고 보고할 수 있다.

1. 코드 수정 후 프로덕션용 빌드를 직접 실행한다.
2. 빌드 오류뿐 아니라 경고, 환경변수 누락, 정적 파일 경로 문제도 확인한다.
3. 프로젝트에 설정된 실제 배포 방식을 확인한다.
4. 배포가 요청 범위에 포함되어 있고 배포 권한이 있다면 실제 배포 명령까지 실행한다.
5. 배포 명령의 종료 코드와 배포 로그를 확인한다.
6. 배포된 공개 URL을 직접 접속하여 HTTP 응답을 확인한다.
7. 공개 URL에서 이번 수정사항이 실제로 반영됐는지 확인한다.
8. 로컬 페이지나 개발 서버가 아니라 실제 프로덕션 URL을 검증한다.
9. 배포 직후 이전 버전이 표시될 수 있으므로 캐시 문제와 서비스 워커 업데이트 여부를 확인한다.
10. 가능하면 모바일 Safari와 Chrome 환경에서 핵심 기능을 점검한다.

배포 완료 판정 기준:

- 코드만 수정됨: 배포 완료 아님
- Git에 커밋됨: 배포 완료 아님
- 원격 저장소에 push됨: 배포 완료 아님
- 로컬 빌드 성공: 배포 완료 아님
- 배포 명령 성공: 아직 최종 완료 아님
- 실제 공개 URL에서 새 버전 확인: 배포 완료

실제 반영 여부를 확인하기 위해 이번 수정에서 식별 가능한 검증 기준을 정한다.

예:

- 새로 추가된 문구
- 변경된 버튼이나 UI
- 수정된 기능의 실제 동작
- 빌드 버전 또는 배포 시각
- 네트워크 요청 결과
- 저장·불러오기 동작

배포 후에는 공개 URL에서 위 검증 기준 중 하나 이상을 직접 확인한다.

배포 실패 시 행동:

1. 실패한 배포 단계와 오류 로그를 확인한다.
2. 원인을 수정한 뒤 다시 빌드하고 재배포한다.
3. 배포가 성공할 때까지 가능한 범위에서 반복한다.
4. 배포 권한, 인증, 환경변수 등 사용자 조치가 반드시 필요한 경우에만 중단한다.
5. 이 경우 “완료”라고 하지 말고 다음을 정확히 보고한다.
   - 배포되지 않은 상태
   - 실패한 단계
   - 오류 원문 또는 핵심 오류
   - 사용자가 해야 하는 조치
   - 조치 후 실행할 명령어

절대 금지:

- 배포하지 않았는데 “배포 완료”라고 보고하는 행위
- 로컬 테스트 결과를 실제 배포 결과로 간주하는 행위
- 배포 버튼이나 명령을 실행했다는 이유만으로 성공을 단정하는 행위
- 실제 URL을 확인하지 않고 “정상 반영됐다”고 말하는 행위
- 배포 실패 로그를 생략하는 행위
- 권한이나 인증 문제가 있는데 성공한 것처럼 표현하는 행위
- Preview 배포를 Production 배포로 잘못 보고하는 행위

최종 보고에는 반드시 다음 내용을 포함한다.

1. 프로덕션 빌드 결과
2. 실행한 배포 명령 또는 배포 방식
3. 배포 성공·실패 상태
4. Production 배포인지 Preview 배포인지
5. 실제 공개 URL
6. 공개 URL에서 확인한 변경사항
7. Safari 및 Chrome 검증 결과
8. 직접 검증하지 못한 항목
9. 남은 오류와 사용자 조치

실제 공개 URL에서 수정사항을 확인하지 못했다면 최종 상태는 반드시 다음 중 하나로 보고한다.

- ⚠️ 코드 구현 완료 / 실제 배포 미확인
- ❌ 배포 실패
- ❓ 배포 권한 또는 환경정보 필요

“✅ 구현·배포·검증 완료”는 실제 공개 URL에서 새 버전이 작동하는 것을 직접 확인했을 때만 사용할 수 있다.

모든 코드 수정 작업에 다음 문장을 적용한다.

> 코드 수정에서 멈추지 말고 실제 Production 배포까지 진행한 후 공개 URL에서 이번 변경사항을 검증하라. 실제 URL 검증 전에는 완료라고 보고하지 마라.

작업을 시작하기 전에 현재 프로젝트의 배포 플랫폼, Production 배포 명령, 공개 URL, 필요한 환경변수를 먼저 확인한다. 확인할 수 없으면 추측하지 말고 배포에 필요한 정보가 무엇인지 명확히 보고한다.

## 9. 앱 내부 Production 버전 및 최근 수정 시각

- 모든 Production 배포는 설정 화면의 앱 정보에 `버전 X.Y · 최근 수정 YYYY.MM.DD HH:mm KST`를 표시한다.
- 버전은 `release.config.json` 한곳에서 관리하고 화면에 직접 중복 입력하지 않는다.
- Production 웹 빌드는 `scripts/build-production-web.mjs`를 사용해 `Asia/Seoul` 기준 빌드 시각을 자동 주입한다.
- Preview와 development 빌드는 Production으로 보고하지 않는다.
- 배포에 실패하면 공개 앱의 버전과 최근 수정 시각은 이전 값으로 남아야 한다.
- 2026.08.15부터 공개 버전은 `1.1`을 기준으로 다시 시작한다.
- Production 수정·배포가 실제 공개 URL에 성공할 때마다 `0.1`씩 올린다. 예: `1.1 → 1.2 → 1.3`.
- 코드만 수정했거나 Production 배포가 실패한 경우에는 버전을 올린 것으로 보고하지 않는다.
- 배포 후 실제 공개 URL의 설정 화면에서 버전과 시각이 새 빌드와 일치하는지 확인한다.
- Safari와 Chrome에서 같은 버전과 시각이 보여야 하며, 다르면 캐시와 서비스 워커를 먼저 점검한다.
- 사용자가 강력 새로고침하지 않아도 최신 버전을 받도록 HTML 캐시와 정적 자산 해시를 확인한다.
- 최종 보고에는 배포 전·후 버전, KST 시각, Production URL, Safari·Chrome 결과, 이전 캐시 잔존 여부를 적는다.
- 앱 내부 버전 또는 최근 수정 시각이 갱신되지 않았다면 배포 작업은 미완료다.

모든 수정 요청의 마지막 기준 문장:

> 이번 수정은 모바일 Safari·Chrome 사용성 회복이 최우선이다. Production 배포 후 앱 내부 버전과 최근 수정 시각을 갱신하고, 실제 공개 URL에서 새 버전·디자인·터치 동작이 모두 반영됐는지 확인하기 전에는 완료라고 보고하지 마라.

## 10. 문제 풀이·출제·데이터 상시 규칙

- 숙어·표현은 핵심 학습 범위이며 핵심 탭과 단어장 범위의 첫 칸에 둔다. 전체 구간 안에만 숨기지 않는다.
- 내용 검수는 숙어의 뜻·해설·한영 예문을 우선한다. 사전 대조 완료 표현 수와 반복 목록 연결 수를 구분하고 전 범위가 검수됐다고 과장하지 않는다.
- 사용자에게 보이는 명칭은 `퀴즈`가 아니라 `문제 풀이`, 하단 짧은 명칭은 `문풀`을 사용한다. 내부 라우트와 코드 식별자는 호환성을 위해 유지할 수 있다.
- 기본 하단 메뉴는 `문풀 → 단어장 → 오답 → 통계 → 설정`이다. 숨긴 기출·북마크 데이터와 화면은 별도 승인 없이 삭제하지 않는다.
- 동의어가 충분하지 않은 범위는 같은 소수 문항을 반복하지 말고 검증된 한국어 뜻 문제로 안전하게 전환한다.
- 한 세션의 최소 75%는 범위 전체를 고르게 순환하고, 약점 복습은 최대 25%로 제한한다.
- 직전 세션 문항, 같은 표제어, 같은 개념의 과도한 중복을 피한다.
- 정답률뿐 아니라 오답·패스·반복해서 고른 헷갈린 답을 다음 출제 우선순위에 반영한다.
- 적응형 기록이 브라우저 로컬 전용인지 계정 동기화인지 보고에서 명확히 구분한다.
- 웹의 문제 이동 제스처는 세로 스크롤을 침범하지 않는 명확한 가로 동작만 인식한다. 버튼 이동은 항상 함께 유지한다.
- 애니메이션 완료 콜백이 누락돼도 뜻 가림, 범위 전환, 문제 이동 같은 기능 상태는 즉시 반영돼야 한다.
- 영영 정의 원문은 재배포가 허용된 정본만 앱에 내장한다. 무료 열람 가능과 재배포 가능을 혼동하지 않는다.
- 영영 정의는 표제어 문자열만으로 붙이지 않고 품사·뜻 단위 매핑과 한국어 검수를 거친다. 검증되지 않은 빈 패널이나 임의 정의를 먼저 배포하지 않는다.
- 영영 정의 원문은 Open English WordNet처럼 재배포 허가가 명시된 자료만 저장하고, Princeton WordNet과 Open English WordNet 양쪽의 저작자·라이선스를 표시한다.
- Wiktionary는 독립적인 품사·뜻 대조 근거로 사용하되, 원문 정의를 앱에 복제하지 않는다.
- 발음은 미국식 실제 녹음이 있고 Wikimedia Commons의 개별 파일 라이선스·저작자·출처가 확인된 경우에만 우선 재생한다.
- 실제 녹음은 CC0, Public Domain, CC BY, CC BY-SA만 허용한다. 그 외이거나 확인되지 않으면 내장하지 않고 `en-US` 기기 합성음을 사용한다.
- 실제 녹음과 합성음을 모두 `공식 사전 녹음`이라고 부르지 않는다. 앱에서는 `미국식 실제 녹음` 또는 `미국 영어 합성음`으로 정확히 구분한다.
- 깊이 학습 해설은 정답을 공개한 뒤에만 보여 주고, 단어장에서는 뜻을 가린 동안 접근성 트리에도 노출하지 않는다.
